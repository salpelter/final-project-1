# Final Project 1

## Why Automate This?

### `NearbyLocationsTest`

- **Risk**: Non-existent or outright wrong locations for branches/ATMs may result in very frustrating user experience for those who rely on them.
- **Business value**: Increases traffic and ensures comfortable user experience, especially for those who opt for in-person banking.
- **Why UI automation appropriate**: This scenario involves a map with crucial data on it, therefore how the user interacts with it needs careful testing.

### `CurrencyConversionTest`

- **Risk**: Incorrect exchange rates or calculation errors may result in financial losses or dissatisfied customers.
- **Business value**: Currency conversion is a frequently used feature in any bank, its accuracy and reliability upholds bank's reputation.
- **Why UI automation appropriate**: UI may cause additional issues even if backend is working properly. Therefore, E2E user experience must be validated.

### `OpenBranchesTest`

- **Risk**: Similar to `NearbyLocationsTest`, presenting incorrect information can lead to negative user experiences, such as incorrect working hours.
- **Business value**: Accurate filters and information are essential for those customers that need planning.
- **Why UI automation appropriate**: Filtering/display logic is necessary to be validated visually and based on current time.

### `OffersTest`

- **Risk**: Incorrect information about offers can reduce customer satisfaction.
- **Business value**: Advantageous offers may attract new customers and keep existing ones.
- **Why UI automation appropriate**: The way offers look may determine whether the customer will decide to make use of them. All important links/buttons must be displayed and functioning properly.

### `MoneyTransferFeesTest`

- **Risk**: Incorrect fees may lead to loss of trust and complaints from customers.
- **Business value**: Clear and accurate fees increase customer trust, leading them to continue using bank's services.
- **Why UI automation appropriate**: UI must display correct fees for the user before they decide to go through with a transfer.

## Selector Strategy

Since a lot of elements have autogenerated attributes, many selector options had to be reconsidered. For this project, mostly XPath selectors were used as they are more robust than CSS selectors, although the latter also came in handy in some cases, offering quick access.

To start with, elements similar to `tbcx-dropdown-popover-item`, `tbcx-text-input`, `tbcx-pw-tab-menu` have proved to be a good starting or relative point in the selection process. They are more or less unique and often allowed to reach the desired element in a few steps.

Lots of selectors in this project contain hardcoded strings. Although it's of the easiest ways to select an element (such as mega menu entry), obviously, it's not the most stable option. If some naming changes, they may break. It's not a particularly serious complication, though, as all selectors are stored in one folder and can be easily replaced. Unless there are major changes introduced, actual code shouldn't break.

Another selector that has seen some use is has to with attributes like `class`. It's often very comfortable to match some containing class or a `href` link in an anchor tag. Something that was very crucial to optimization is filtering by `active` class when selecting a map marker. Initially, I grabbed the whole collection for filtering which made the code run for _minutes_, but luckily realized I could just look for the element based on presence of the aforementioned class.

## Flaky Test Awareness

One of the scenarios in this project involved searching for currently open branches (based on real current time). Due to the fact that in some cities there aren't many branches, especially 24/7 ones, the tests often fails, throwing an exception (something like _"No map markers were found."_). And due to the structure of the test class, it was not an option to use a `RetryAnalyzer`, although I wanted to. The test needs setup, while `RetryAnalyzer` would only run failed tests. This makes the test flaky and not much can be done realistically to prevent it.

Some tests may also suffer issue because of intercepted clicks caused by overlaying elements. One of them is the cookie prompt. I easily solved this problem by denying cookies before each class execution, therefore reducing one more "variable" to keep in mind.

## Mobile ≠ Desktop

The biggest difference between mobile and desktop was luckily the mega menu. There was a hamburger menu that had to be clicked on to open the same menu, although with folded sections.

In some cases there were several elements matching the same selector, where only one was visible. My guess is that each of them is related to different screen sizes. Instead of grabbing them using an index, I easily filtered them dynamically, by using the `visible` condition.

There weren't many UI risks to be concerned about as most features, as well as assertions, worked the same across all scenarios. The only difference is a more compact look, since mobile devices are obviously smaller.
